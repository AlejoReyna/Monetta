# Monetta storefront motion research

22 October 2026 · Research and isolated demonstrations only

**Recommendation:** harden existing panel transitions and truthful cart feedback first. Keep native gallery navigation, static variant semantics and static disclosure bodies. Add small keyboard-equivalent card/save cues only if evaluation supports them. Keep the current persistent mobile purchase dock; its contextual alternative in the lab is exploratory.

The lab contains six evaluation moments, not six mandatory animation features. The sixth deliberately exposes the costs of a lower-priority idea. Motion should resolve uncertainty about state or location; product titles, prices, essential content and purchasing controls remain readable immediately.

## Browser, accessibility and performance research

The following are documentation facts checked on 22 October 2026. Timings, amplitudes, rankings and adoption decisions are design judgments, not requirements from these sources.

| Primary source | Verified guidance and consequence |
|---|---|
| [W3C SC2.3.3](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html) | Disable nonessential interaction-triggered motion. This criterion is **AAA**, not AA. The lab removes translation/scaling as well as transitions in reduced mode. |
| [Mozilla reduced-motion](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-motion) | Widely available; reflects a device/system preference. CSS covers transitions; `matchMedia` covers JS effects and reacts to preference changes. Forced full is clearly an evaluation override. |
| [W3C modal pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/), [Mozilla dialog](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/dialog) | Modal focus belongs inside; Escape and visible close work; return to invoker. `showModal()` provides top-layer modal semantics and outside inertness. APG is implementation guidance. Core dialog is widely available since2022; no dependency on newer `closedby` features. |
| [W3C SC4.1.3](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) | AA status feedback should be programmatically available without moving focus. Local success/error/pending messages use status regions. Screen-reader announcement quality still needs testing. |
| [W3C SC2.4.11](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html) | AA focus must not be entirely obscured by author-created UI. Fixed bars need content reserve, scroll padding and a focused-control visibility guard. |
| [W3C SC2.2.2](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html) | Automatically initiated motion lasting over5s alongside other content generally needs a stop/pause/hide mechanism unless essential. No persistent decoration or autoplay is proposed. |
| [Google rendering guide](https://web.dev/articles/animations-guide), [Shopify performance guidance](https://shopify.dev/docs/storefronts/themes/best-practices/performance/use-transform-for-animations) | Prefer transform/opacity, then inspect actual rendering. Neither property choice nor screenshots prove compositor-only rendering, zero CLS, or smoothness. Avoid speculative blanket `will-change` and animated shadow/height/blur. |
| [Mozilla Element.animate](https://developer.mozilla.org/en-US/docs/Web/API/Element/animate), [IntersectionObserver](https://developer.mozilla.org/en-US/docs/Web/API/Intersection_Observer_API), [container queries](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Containment/Container_queries) | Stable browser capabilities support short cancelable image/icon effects, threshold observation and specimen-responsive layouts. The lab uses CSS for panels/card/chevron/bar; vanilla JS handles asynchronous state and focus. WAAPI absence falls back to immediate feedback. Observer absence leaves the inline CTA usable. No animation library is proposed. Container-query absence needs narrow-layout CSS fallback in older browsers. |
| [Chrome cross-document transitions](https://developer.chrome.com/docs/web-platform/view-transitions/cross-document?authuser=485), [Mozilla @view-transition](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@view-transition) | Conventional multi-page navigation can transition without a SPA; both documents must opt in, share origin and avoid intermediate cross-origin redirects. MDN currently marks this limited availability. Defer; unsupported browsers should navigate normally. Hosted checkout/account are separate boundaries. No experimental API is used in this lab. |

The lab's layout containers are an evaluation convenience, not a production integration requirement. Current evergreen browsers are the intended target. Native details and ordinary content remain usable if animation JavaScript fails; simulated controls need JavaScript. Full older-browser fallbacks and cross-engine validation remain implementation work.

## Design conclusions

Use180ms for bounded confirmation/chevrons and280ms for panel or optional loaded-media changes. Keep480ms available for a carefully justified editorial group, but there is no strong reason to use it in these purchasing interactions. **The absence of a480ms effect in the proposed first set is intentional.** ×2 is an inspection setting only. Simulated220/650/1200/1800ms waits represent loading, not motion tokens. The card's650ms explicit preview hold is a lab control; actual hover/focus lasts only while active.

Static baselines perform every action with0ms decorative motion. Reduced mode preserves actual simulated pending time while eliminating nonessential movement. A request starts at activation, never after an entrance; controls/semantic selection do not wait for decoration. During loading the gallery retains its old labeled image and latest intent supersedes old work. Errors are static, persistent and actionable. Count/total changes never tween invented values.

The current purchase dock already solves reach on mobile. Its contextual experiment tests whether reducing duplicate fixed actions earns its added lifecycle/focus complexity. It is not in the first implementation set. Likewise the image crossfade is a useful comparison, not a mandate to replace the existing native gallery.

**Mobile:** prioritize reversible panels, explicit pending/confirmed feedback and clear static selection; keep the persistent safe-area purchase dock. **Desktop:** prioritize keyboard-equivalent card/image cues and responsive modal orientation; keep purchase information in a stable column. **Shared:** native disclosure, truthful status text, stable media, latest-request guards and fully static reduced-motion behavior offer the greatest benefit. Static typography, product grids, prices, errors and header geometry best fit Monetta across both.
