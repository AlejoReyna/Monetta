# Prueba de push desde Shopify y problemas encontrados

Entorno: Monetta Staging, Android Emulator `Monetta_Demo_API35` (API 35), macOS. Fecha: 17 de noviembre de 2026.

## Entrada de texto en el emulador

**Reportado por el usuario:** no puede introducir texto en el simulador, incluido el código de verificación de Shop durante el inicio de sesión.

**Evidencia:** el campo de verificación estaba habilitado y enfocado según UI Automator. El envío de texto mediante `adb shell input text` sí fue aceptado y permitió completar el acceso. No se conserva el código de verificación en este documento.

**Diagnóstico pendiente:** el AVD tiene `hw.keyboard=no`; el teclado virtual está configurado con `show_ime_with_hard_keyboard=1`. Estos valores no prueban la causa del fallo de entrada desde el host. No se considera resuelto el problema reportado por el usuario.

## Configuración de inicio de sesión

La configuración local de staging tenía `CUSTOMER_ACCOUNT_CLIENT_ID` vacío y el shop ID de producción. Se recuperó el client ID público de la configuración de Customer Account del canal Headless de Monetta Staging y se corrigió el shop ID para coincidir con los endpoints de descubrimiento y el esquema de retorno Android de staging. APK recompilado e instalado. Acceso con Shopify confirmado en el emulador.

## Pantalla de notificaciones desconectada

Las entradas de Cuenta y del menú abrían `openNotifications` sin pasar `NotificationController`; la pantalla mostraba que las notificaciones no estaban configuradas aunque la app tenía `NotificationScope`.

Corrección: `openNotifications` resuelve el controlador compartido desde `NotificationScope` cuando no se proporciona uno explícito y conecta las preferencias y el destino de apertura.

## Estado de la demostración

Completado: registro del dispositivo, envío de prueba dirigido desde Shopify, recepción en Android y apertura de Inicio en la app. Shopify muestra **1 entregado, 1 abierto y 0 fallidos**. El archivo anterior `recorrido-parcial-sin-envio.mp4` sigue siendo sólo una captura de diagnóstico.

## Bloqueo inicial resuelto: App Check deshabilitado

La API de Firebase respondió HTTP 403 `SERVICE_DISABLED` al intentar registrar el emulador de staging mediante un token de depuración. Servicio: `firebaseappcheck.googleapis.com`, proyecto `monetta-catalog-staging-edfb8` (139790628419).

El intento de habilitar el servicio con la identidad del backend respondió HTTP 403: falta `serviceusage.services.enable`. La sesión de Google Cloud abierta en el navegador tampoco encuentra este proyecto. Se solicitó acceso con la cuenta administradora. No se modificó la validación del backend ni se omitió App Check.

La configuración **local y no versionada** de staging ahora usa `FIREBASE_APP_CHECK_DEBUG=true` para este emulador. Falta registrar su token de depuración cuando el proyecto esté accesible; el token no se incluye en el informe.

Validación de la corrección de navegación: pruebas de pantalla y controlador, incluida una regresión que abre avisos desde una ruta con `NotificationScope`, abre las preferencias y entrega el destino al controlador compartido.


## Reanudación y resultado final (01:44, America/Monterrey)

Con la cuenta administradora se habilitó App Check y se registró el proveedor de depuración del emulador. La validación del backend permanece activa.

Correcciones desplegadas en staging:

- `FirebaseAppCheckVerifier` acepta la respuesta exitosa documentada de Firebase (`{}` o `alreadyConsumed` booleano), sin exigir el campo inexistente `appId`.
- La consulta de audiencia convierte explícitamente el parámetro de fecha a `timestamptz` antes de restar intervalos.
- Se actualizó la máquina de notificaciones a la misma imagen desplegada del API; se conserva el worker de mantenimiento de rewards en `fly.toml`.

Evidencia de la prueba real:

- Borrador: `14ee5bed-f463-4b5d-87a1-0bee67bf1414`.
- Campaña dirigida de prueba: `1629f3a1-a3ca-49f2-9374-ebfbfee2e296`.
- Entrega: `d5d8c9e5-e3a5-4922-9acd-107813b5b01e`, estado `accepted`, aceptada a las `2026-11-17T07:44:18.740Z`.
- Una interacción `opened` confirmada en PostgreSQL; panel Shopify: enviado, audiencia 1, entregados 1, abiertos 1, fallidos 0.
- La notificación de Android abrió Inicio en la app. No se envió la campaña general; se usó **Enviar prueba** con el ID del emulador.
- Se restauró el horario silencioso de este dispositivo a **21:00–09:00** después de la prueba.

Artefactos en `docs/previews/push-demo-2026-11-17/`:

- `demo-shopify-push.mp4`: video de 67 segundos, Shopify y emulador juntos; cálculo de audiencia, envío dirigido, recepción y apertura. Se recortó el inicio de preparación del emulador; el tramo conservado es continuo y sin audio.
- `01-notificacion-recibida.png`: aviso real en la bandeja de Android.
- `02-notificacion-abierta.png`: Inicio abierto y contadores de Shopify.

Validación: revisión de tipos TypeScript y 10 pruebas de App Check/API aprobadas en esta reanudación. Las 8 pruebas Flutter de pantalla/controlador habían pasado en la sesión anterior.

El emulador requirió reinicio y mostró un bloqueo temporal de System UI durante el arranque; se recuperó antes del envío. La causa del problema original de escritura desde el host sigue pendiente. La etiqueta del panel dice «Producción», aunque el host y la tienda usados fueron los de staging.


## Demo de tres mensajes con Shopify visible (02:02)

Se grabaron en Shopify tres envíos dirigidos al emulador, con título Monetta y los cuerpos exactos: «Hola Miguel», «Esta es una notificacion desde un Android» y «Saludos y cuates». El video `docs/previews/push-demo-2026-11-17/tres-notificaciones-shopify.mp4` muestra redacción, revisión, botón Enviar prueba y recepción en Android lado a lado. Se conserva aparte el video anterior que mostraba sólo el teléfono.

Se corrigió un bloqueo adicional: la materialización aplicaba el límite diario también a las campañas de prueba. Ahora únicamente las campañas `kind=test` con segmento `device` omiten ese límite; campañas generales, consentimiento, permisos y horario silencioso conservan sus verificaciones. La audiencia general puede mostrar 0 por el límite diario mientras el envío de prueba dirigido sí es elegible. Se desplegó API y worker de notificaciones; revisión de tipos y 10 pruebas aprobadas. Los tres envíos de la toma final quedaron aceptados. El horario silencioso del emulador se restauró a 21:00–09:00 al terminar.
